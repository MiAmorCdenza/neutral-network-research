# 运行时与语言策略（Runtime Strategy v0.1）

- 定位：回答「用什么语言/运行时实现这套机制」；记录语言分阶段策略、移植边界与决策门。
- 结论一句话：**研究壳（Python）+ 可替换机制核心**——核心先以 PyTorch 密集张量实现（买研究速度），按剖面数据决定何时移植到 Triton/Rust；若最终承诺事件驱动形态，核心重写为 Rust/C++ 事件引擎（NEST/Brian2/GeNN 模式）。规格中的纯函数/显式状态契约已为无损移植留缝。

## 1. 效率拆解：「Python 慢」到底慢在哪

| 成本类别 | 内容 | 谁在算 | Python 的责任 |
|---|---|---|---|
| ① 密集线性代数 | matmul/卷积（占 FLOPs 大头） | C++/CUDA 内核（ATen/cuBLAS） | 无——只发指令 |
| ② 逐连接状态维护 | 资格迹 E、STP(u,x)、Pr、延迟、健康度 | elementwise 内核 | 慢在**每次小内核的调度启动**（~5–20µs × 每步 30–50 次），不在计算本身 |
| ③ 控制流/事件驱动/结构变更 | 时钟嵌套、稀疏事件、L6 增删单元、锁检查 | Python 解释器/GIL/图断裂 | **真实短板，全责** |

量化（V0 规模：64×64×2 隐层，batch 128）：每步 matmul ≈ 1M MACs——微小；CPU 上 Python 编排可占步时 20–50%；但 20k 步总时长仍为分钟级。GPU 上小张量的启动开销占比反而更高。**结论：小网络阶段 Python 开销真实但可容忍；大网络阶段被 matmul 摊销；事件驱动形态会重新暴露它。**

## 2. 形态错配才是根本问题

- 本项目的生物路径**根本不用 autograd**（三因素全程 no_grad + param.data 手动更新）——PyTorch 的王牌只服务 D4-1 的 backprop 基线。我们在用框架约 30% 的价值。
- 若承诺**率编码 + 批量密集**（当前规格形态）→ 瓶颈在 matmul，任何带 BLAS/CUDA 的方案等价；语言只影响编写速度，不影响训练速度上限。
- 若承诺**真事件驱动稀疏**（L0/L9 极致形态：只算活跃单元、逐尖峰调度）→ 密集张量框架全部不适配（包括 Rust+tch/candle 的张量形态）——需要事件队列引擎（Brian2 代码生成 / NEST C++ 核心 / GeNN GPU 尖峰仿真的既有模式：编译核心 + 脚本前端）。
- 结构自演化（L6 增删单元）与静态图编译（JAX jit、torch.compile）天然冲突——每次结构变更都要重编译。

## 3. 候选方案判断

| 方案 | 密集代数 | 逐连接状态 | 控制流/事件 | 基线 autograd | 研究迭代速度 | 判断 |
|---|---|---|---|---|---|---|
| Python+PyTorch | ★★★ | ★★（启动开销） | ★ | ★★★ | ★★★ | V0 阶段正确 |
| JAX | ★★★（jit） | ★★★（scan） | ★（静态图） | ★★★ | ★★ | 静态图与 L6 冲突；事件驱动不适 |
| C++/libtorch | ★★★ | ★★★ | ★★ | ★★★ | ★ | 开发慢；仍是张量形态 |
| Rust（tch/candle/burn） | ★★★ | ★★★ | ★★ | ✗/部分 | ★ | 无 autograd → 手写基线；生态年轻 |
| Rust 自研事件引擎 | ★（自写） | ★★★ | ★★★ | ✗ | ★ | 事件驱动的终极形态；后置 |
| **混合（推荐）** | 研究壳 Python + 核心分阶段 | | | 壳内保留 | ★★→★★★ | 见 §4 |

## 4. 三阶段策略（推荐）

- **阶段一 V0–V2（验证学习规则）**：Python+PyTorch，密集形态。目的不是效率，是用最快速度证明「三因素 + 五选择压 + 资格迹可训练」（D4 六指标，约 22+ 次训练运行——总线扫描/延迟消融/种子扫描/自校准消融）。**瓶颈是实验吞吐，不是单步速度。** 机制实现为**每层一个融合步函数**（L1.F9 synapse_forward 形态），不逐机制散调——这同时就是未来的移植单元。基线 autograd 免费获得。接受小网络 20–50% 编排开销。
- **阶段二（机制核心编译化，以剖面数据为门）**：V0 完成后 profile；若机制开销 >20% 步时：将融合步函数移植 Triton（GPU）或 Rust/PyO3（CPU，小网络 CPU 足够且最快）——每层一个导出函数，状态全显式进出（与规格 [递推状态] 契约一致）。预期收益：小网络 3–10×。
- **阶段三（事件驱动承诺门，V6 时决策）**：若启用真事件驱动 → Rust/C++ 事件队列引擎，Python 退化为研究壳（配置/评估器/分析）。00-kernel 的注册表 + 纯函数 + 显式状态契约即该引擎的直接输入。

## 5. 现在就要钉死的移植边界（与语言无关的形态要求）

1. 每机制 = 纯函数/递推函数 + 显式状态 buffer（规格已强制）——无隐式全局、无闭包捕获网络对象；
2. 融合步函数边界：每层一个 `step(state, x, clocks) -> (y, state')`；跨机制通信只走 state；
3. 数据布局：逐连接状态与权重**同形状**（E 与 W 同形）——保证 elementwise 内核可融合、可并行；
4. 配置/注册表序列化（K4）——核心语言无关；
5. 基线 autograd 隔离在 eval 模块——移植核心时基线可留在 Python 不动。

## 6. 结论

- 用户直觉在**长期/事件驱动/极致保真**目标下正确：机制维护与结构演化终局属于编译型语言。
- 在 **V0 验证期**，PyTorch 不是训练瓶颈，研究速度才是；「自定义内容很多」与语言无关——这些机制在任何语言里都要写，语言只改变运行开销与编写速度。
- 正确姿势：承认双层架构（研究壳 + 可替换核心），阶段一用 PyTorch 买时间，用规格契约保证无损迁移，用 profile 数据而非直觉决定何时移植。
